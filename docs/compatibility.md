# Compatibility

What has actually been exercised, and by what. There are two kinds of evidence
here and they answer different questions:

- **Repository mocks** — the servers the test suite starts itself. They prove the
  two runtimes agree with each other and with the contract, on every CI run.
  They cannot prove interoperability: a mock written alongside the client never
  disagrees with it about certificates, operation limits or continuation points.
- **Real-server conformance** — the [conformance harness](#real-server-conformance)
  driving both runtimes through the same scenarios against an OPC UA server this
  project does not control, with the result published as a dated JSON file.
  That is the only evidence behind a "supported" below.

Neither is a vendor certification.

#### What the levels mean

A level is about one server **product and version** — as the server itself
reports it in BuildInfo — one package version, and the configuration the result
records (security modes, user identities, which features were mapped). A
different version or firmware of the same product is unverified until it has a
result of its own.

- **Supported** — a published result from **both** runtimes in which every
  scenario that ran either passed or found a feature the server itself says it
  does not offer (*unsupported optional feature*). Nothing failed.
- **Partially supported** — a published result from both runtimes in which at
  least one scenario failed and was classified: a project bug, a client-library
  limitation or a server limitation. Each is listed under *Findings* with the
  reason, and everything else passed. Read the findings before relying on the
  affected feature.
- **Unverified** — no published result: the server was never run, or only one
  runtime was, or a failure has not been classified. Prosys, Unified Automation,
  Softing, KEPServerEX, Ignition, Siemens, Beckhoff and every other server not in
  the table above are **unverified**. Both runtimes use general-purpose OPC UA
  client libraries and speak no vendor-specific protocol, so they are *expected*
  to work against a compliant server; expected is not tested.

#### What the outcomes mean

The harness decides *pass*, *unsupported optional feature* and *not configured*
itself. A failure it can only report; a person classifies it, in the config's
`triage` list, and a result with an unclassified failure fails `check` and
cannot be published.

- **pass** — the behaviour held on that runtime.
- **project bug** — this project did something wrong, and the fix belongs here.
- **library limitation** — `python-opcua` or `node-opcua-client` cannot do it;
  the fix is a library change or the library migration
  ([#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144)).
- **server limitation** — the server does something the specification does not
  allow, or refuses something it advertises.
- **unsupported optional feature** — the server says it does not offer this: no
  endpoint for the security mode, no history capability, no aggregate
  functions, no user token of that type. OPC UA makes most features optional;
  this is not a failure of anything.
- **not configured** — the run did not exercise it: the config maps no node for
  it, or the scenario needs something the setup lacks (a user account, a lab
  server the harness can restart).

#### The servers behind the published results

Both ran on the machine the harness ran on, started by the harness itself, so
the restart scenarios could take the server away and give it back. Neither is a
commercial product.

- **open62541 1.5.8** (C, [open62541.org](https://www.open62541.org/)), built
  from source by
  [`compatibility/labs/open62541/build.sh`](../compatibility/labs/open62541/build.sh)
  with encryption, historizing and Alarms & Conditions enabled. open62541's own
  example servers each show one feature, so
  [`lab_server.c`](../compatibility/labs/open62541/lab_server.c) assembles the
  SDK's documented building blocks into one address space configured the way a
  deployment is: a client-certificate trust list, per-user permissions that
  differ from a node's AccessLevel, operation limits small enough to matter
  (MaxNodesPerRead 40, MaxNodesPerWrite 20, 100 references per browse
  response), raw history that pages every 25 values, and a retained alarm.
  Every OPC UA service is answered by the open62541 stack; the file only builds
  the address space.
- **Eclipse Milo 1.1.7** (Java, [eclipse.dev/milo](https://eclipse.dev/milo/)),
  the example server from Milo's own repository, unmodified. It has no
  history, no aggregates and no conditions, and offers no `Sign`-only endpoint,
  which is exactly what its *unsupported* cells say.

Neither shares code with `python-opcua` or `node-opcua`, which is what makes them
evidence of interoperability. The node-opcua sample server and the `asyncua`
example server are deliberately **not** in the matrix: the first is the Node
runtime's own stack talking to itself, and the second descends from
`python-opcua`. Either is a useful regression target; neither is independent
evidence. Many embedded servers are built on open62541, but a product adds its
own configuration, limits and permissions on top — a result for the SDK is not a
result for a device built with it.

#### Not covered yet

- **An uncertain control outcome.** A write or method call in flight when the
  session dies must be reported as "may or may not have happened", never
  retried; both runtimes are pinned to the same wording by
  [`tests/fixtures/uncertain-outcome.json`](../tests/fixtures/uncertain-outcome.json),
  but losing the session between request and response needs fault injection
  inside the connection, which the harness does not have.
- **Namespace reordering on a vendor server.** Only a lab server can be told to
  come back with its namespaces in a different order, so
  `recovery.namespace-reorder` is *not configured* everywhere else. Write vendor
  configs with `nsu=` node ids so the harness re-resolves them every session.
- **Historical events and aggregates** — neither published server offers them;
  the scenarios exist and report *unsupported*.
- **Keep-alive tuning and long outages.** The restart scenarios cover a server
  that goes away for seconds; hours, network partitions and session-lifetime
  expiry are not exercised.

#### Run it against your server

```bash
cd tests
uv run --no-sync python -m conformance run --config my-server.json
uv run --no-sync python -m conformance render   # regenerate the matrix above
uv run --no-sync python -m conformance check    # what the unit suite enforces
```

Both runtimes run by default (`--runtime python` or `--runtime node` for one);
`--only <scenario>` repeats a single scenario while triaging. Each failing
scenario's server stderr is written to the run's temporary directory and the
path printed — it is for you, and never part of the result. `--external` skips
the config's `lab` command for a server that is already running.

A config is JSON; [`compatibility/labs/milo.json`](../compatibility/labs/milo.json)
and [`open62541.json`](../compatibility/labs/open62541.json) are complete
examples. The parts that matter:

- **`endpoint`** — a URL, or `{"env": "VARIABLE"}`.
- **`security`** — the `policy` and the `modes` to exercise, the `default`
  channel for everything else, and `clientTrust`: `"enforced"` if the server
  refuses client certificates it has not been told to trust (the negative
  certificate scenario needs this), `"trust-all"` or `"unknown"` otherwise. The
  harness generates throwaway client, user and impostor certificates for every
  run; `clientCertificate: {"cert": …, "key": …}` supplies your own, as paths.
- **`identities`** — `anonymous`, `user` and `x509`. **Credentials are always
  environment references**, `{"env": "VARIABLE"}`: a literal username or
  password, or key material instead of a path, is a load error.
- **`nodes`** — the node map: which of *your* nodes stand in for a scalar of
  each type, an array, a structure, a writable node and the value to write, a
  node the account may not write or read, a method with its arguments and output
  types, a historized node, a changing node, the event source and the alarm
  source. Anything not mapped is *not configured*. Use `nsu=<namespace URI>;…`
  ids: the harness resolves them against the server's NamespaceArray each
  session.
- **`lab`** — optional: a command the harness starts the server with, which is
  what enables the restart scenarios. Leave it out for a server you run
  yourself.
- **`triage`** — the classification of each failure, with a `summary` and an
  optional `tracking` issue.

**What a result never contains:** the endpoint, any node id, any value read or
written, any username, password or key. The scenarios record only status-code
names, data-type names, counts and booleans; tool output is redacted before it
is kept; and the finished document is checked for endpoints, node ids, key
material and the run's own credentials before it is written — one that fails
the check is not written at all. It does record what the server says about
itself (BuildInfo) and what its endpoints offer, because a result that cannot
say which server it is about is not evidence.

Test only on equipment you are authorised to use. The harness writes the nodes
you map as writable, calls the method you map and acknowledges alarms: point it
at a simulator or an isolated lab, never at a running process.

## Runtimes and clients

- **Python 3.10+**, **Node 22.13+** — the floors the manifests declare.
- CI runs Python 3.10 with Node 22, Python 3.13 with Node 22, and Python 3.13
  with Node 24.
- **Transport: stdio only.** The client must be able to launch a local stdio MCP
  server, or install the Claude Desktop `.mcpb` bundle. There is no HTTP
  transport ([#14](https://github.com/IndustriAgents/OPCUA-MCP/issues/14)).
- **What reaches the plant is identical on both runtimes.** Date/time parsing,
  write conversion per data type, method-argument typing, OPC UA status severity
  and the operator policy's number parsing are each one table under
  [`tests/fixtures/`](../tests/fixtures/) that both runtimes' unit suites run
  ([#157](https://github.com/IndustriAgents/OPCUA-MCP/issues/157)). Timestamps
  must carry a zone (`Z` or an offset); one without is refused on both.
- Client configurations in [docs/install.md](install.md) are worked
  examples, not a per-client certification matrix. `--install claude-desktop`
  is the only client integration with its own tests.

## Runtime differences

Both runtimes are first-class
([ADR 0001](adr/0001-two-first-class-runtimes.md)): one contract, one suite,
one release gate, one version. What they do **not** share is declared in
[`contract/runtime-differences.json`](../contract/runtime-differences.json),
which is the authoritative list; this table renders it, and
`tests/unit/test_runtime_differences.py` fails if an id is missing here or a
checkable fact behind an entry changes. Every entry is deliberate — allowed by
the ADR and expected to stay until a library change retires it (usually
[#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144), the move to
`asyncua`).

| ID | What differs | Could retire it |
|---|---|---|
| `security-policies-aes` | `Aes128_Sha256_RsaOaep` and `Aes256_Sha256_RsaPss` are Node only; Python refuses them at startup, naming the Node runtime | [#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144) |
| `certificate-file-encoding` | Python reads a certificate or key as PEM only when it is named `*.pem`; Node sniffs the contents. Name every file `*.pem` and both work | [#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144) |
| `mcp-protocol-generation` | Python's `mcp` 2.x serves MCP protocol revisions up to 2026-07-28; Node's SDK 1.x up to 2025-11-25. Same tools and results either way; change notifications are offered on neither | — |
| `mcpb-bundle` | The Claude Desktop `.mcpb` bundle is Node only | — |
| `mcp-registry-listing` | The MCP Registry metadata (`server.json`) lists the npm package only | — |
| `cli-command-alias` | npm also installs the command `opcua-mcp`; the documented `opcua-mcp-server` is on both | — |
| `reconnect-mechanism` | node-opcua repairs a dropped channel in the background and keeps the same session; Python builds a new session when the next call needs one. Same settings, same waits, same recovery | [#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144) |
| `transport-limit-enforcement` | The same inbound message bounds, enforced by node-opcua on Node and by a local patch to python-opcua on Python (CVE-2022-25304) | [#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144) |
| `opcua-library-maintenance` | Python's OPC UA library is unmaintained; Node's is maintained. See [SECURITY.md](../SECURITY.md#cve-2022-25304--unbounded-chunk-reassembly-in-python-opcua) | [#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144) |
| `client-pki-on-disk` | node-opcua keeps a PKI folder of its own, with a generated default certificate and the server certificates it has seen; Python writes nothing | — |

| `concurrency-model` | Latency, throughput and memory differ and are not promised to match; the bounds and waits are | [#144](https://github.com/IndustriAgents/OPCUA-MCP/issues/144) |
| `audit-file-rename-on-windows` | On Windows the Python server holds `OPCUA_AUDIT_FILE` so it cannot be renamed or deleted while running; use copy-and-truncate rotation there. Node allows rename rotation everywhere | — |

### Known divergences being fixed

Anything a client can observe that is not in the table above is a bug, not a
difference — report it with the bug template's *both runtimes, behaving
differently* box. Those known today are **not** allowed differences and are
being fixed in both runtimes:

- [#157](https://github.com/IndustriAgents/OPCUA-MCP/issues/157) — found while
  writing ADR 0001. The group that reached the plant is fixed: dates, write
  conversion, method-argument types, Good-subcode statuses and the policy's
  number parsing now follow one rule on both runtimes (see
  [Runtimes and clients](#runtimes-and-clients)). So are subscription
  parameters, event subscriptions after a reconnect, policy-file validation,
  the startup check order, auditing of refused control calls and signal
  handling. Still open: result and error formatting and `--install` details.
- [#136](https://github.com/IndustriAgents/OPCUA-MCP/issues/136) — with
  `OPCUA_RECONNECT_MAX_RETRY=-1` and an unreachable endpoint, the Node server may
  never open its MCP transport, and the numeric reconnect settings accept
  different spellings on each runtime.

Until #136 is fixed, do not rely on `OPCUA_RECONNECT_MAX_RETRY=-1` with the
Node runtime.

## Security coverage

[`tests/e2e/test_secure_connection_e2e.py`](../tests/e2e/test_secure_connection_e2e.py)
drives both runtimes against a fixture that offers `Basic256Sha256` endpoints
only, with certificate-based channel security, username and X.509 user
authentication, and checks that an unsecured client is refused, that passwords
never reach the logs, and that a pinned server certificate (`OPCUA_SERVER_CERT`)
connects while an impostor's is refused.
[`test_security_startup.py`](../tests/e2e/test_security_startup.py) checks that
an unusable security configuration is rejected at startup.

That is coverage of *this project's* handling of security. Against real servers
the [conformance harness](#real-server-conformance) adds the same checks with
someone else's stack on the other end: every security mode the server offers,
certificate pinning, an impostor's pinned certificate refused, a client
certificate the server does not trust refused, username, a wrong password
refused, and X.509 user authentication. It is still not interoperation with a
vendor PKI — no CA-issued certificates, no revocation lists. Without `OPCUA_SERVER_CERT` the server certificate is taken
from the endpoint description and not verified, and neither runtime validates
against a CA trust list — see [SECURITY.md](../SECURITY.md#connection-security-important)
and [#134](https://github.com/IndustriAgents/OPCUA-MCP/issues/134).

## Tool policy coverage

[`tests/e2e/test_policy_e2e.py`](../tests/e2e/test_policy_e2e.py) runs both
runtimes under the default `observe` profile and under `operator` with explicit
allowlists, and checks that a hidden control tool is still refused when called
directly. Policy is enforced per call, not only at tool-listing time.

## Resilience and diagnostics coverage

[`tests/e2e/test_resilience_e2e.py`](../tests/e2e/test_resilience_e2e.py) drops a
mock server under both runtimes and asserts the session recovers, including the
data-change subscriptions held across the outage, and that a server unreachable
at startup does not stop either server from starting.
[`test_diagnostics_e2e.py`](../tests/e2e/test_diagnostics_e2e.py) checks that
`get_server_status` answers while disconnected and that both runtimes return the
same fields. The backoff arithmetic itself is pinned in
[`tests/unit/test_reconnect.py`](../tests/unit/test_reconnect.py).

This is coverage against the local mocks. The conformance harness's `recovery`
scenarios restart a real server under an open session — a read while it is down
must fail rather than hang or report Good, the same MCP session must read again
once it is back, and a data-change subscription must resume — but only for a
server the harness starts itself. How a given vendor server behaves across a
real network outage — session lifetimes, certificate rotation on restart, long
partitions — is **Unverified**.

## Report a result

The strongest report is a result file: run the
[harness](#run-it-against-your-server) against your server, triage any failure,
and open a pull request with the file from `compatibility/results/` and the
re-rendered matrix. It carries everything a row needs and nothing it must not —
no endpoint, node id, value or credential — so it is safe to publish as it is.
Keep your config to yourself if its node map says more about your plant than
you want public; the result does not include it.

Where running the harness is not possible, open a
[compatibility report](https://github.com/IndustriAgents/OPCUA-MCP/issues/new?template=compatibility_report.md)
that names the server product and version, the package version, the runtime,
the MCP client, the security and identity settings, and the tools that were
called. It is useful evidence, but a server moves out of **Unverified** in the
matrix only with a published result.

Test only on equipment you are authorised to use; use a simulator or an isolated
lab for writes, method calls and alarm acknowledgements. Do not include
credentials, private keys, internal endpoint names or production process data in
a report.
