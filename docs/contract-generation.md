# Contract schemas and generated types

`contract/tools.json` is metadata validated by `contract/contract.schema.json`,
which uses JSON Schema draft 2020-12. Each embedded input/result schema also
names that draft. `contract/schemas.json` is the generated, normalized `$defs`
catalogue for external tooling and parity tests.

Run from the repository root:

```sh
uv run python scripts/contract_codegen.py
uv run python scripts/contract_codegen.py --check
```

Generated artifacts are **committed**. CI runs check mode in its fast job and
in the shared conformance action used by CI, release and publish. Check mode
validates metadata, checks every embedded schema against the official draft,
rejects unsupported/misspelled keywords and compares every generated byte.
Generated TypeScript and Python files use the generator's fixed format; do not
hand-format or edit them.

The generator emits an input and result type for every tool, the structured
record types, completeness, and tool-name/input/result registries. Python uses
`typing_extensions.TypedDict`, `Required` and `NotRequired` to support Python
3.10. TypeScript exports `ToolInputs`, `ToolResults` and `ToolHandlers` keyed by
`ToolName`. Python registration consumes the generated names; TypeScript's
exhaustive dispatch switch fails typechecking when a new name lacks a case.
Implementation of OPC UA operations is still handwritten.

The supported authoring profile is `contract/schema-profile.json`. Its keywords
are standard draft-2020-12 keywords, with semantics supplied by
[Ajv](https://ajv.js.org/json-schema.html) and
[jsonschema](https://python-jsonschema.readthedocs.io/en/stable/validate/).
The profile deliberately excludes references and combinators until the static
type generator can represent them faithfully. An unknown keyword fails
creation/checking rather than being silently ignored. To expand the profile,
update generation and the cross-runtime differential corpus in the same PR.

Ajv runs in strict schema mode with no coercion, default insertion or removal
of additional properties. Python uses Draft202012Validator and excludes
non-finite numbers from the JSON number type. Neither validator receives
live OPC UA type information: node resolution, server datatypes and policy
checks remain separate semantic checks.

`validation.py` and `validation.ts` translate engine errors into
`ValidationRefusal(code, argument, message)`. They retain contract-owned
messages such as `missingArgument`, `unknownArgument` and `belowMinimum`;
additional supported constraints use `schemaConstraint`, naming the keyword.
Library prose is not exposed. Ordering is deterministic: container constraints
precede child constraints, required names follow schema order, and children
follow declared property order and array index. Element corrections precede
uniqueness corrections, because Ajv can omit uniqueness errors for mistyped
elements. Nullable optional fields mean
“apply the existing default”; required nulls remain missing-argument refusals.
The schemas now declare those existing rules explicitly.

Shared legacy fixtures preserve existing correction messages. A deterministic
corpus mutates every tool's inputs and exercises additional numeric, collection,
string and nested constraints, comparing acceptance, project code, path and text
between the actual installed validators. E2E result parity uses the standard
validator, including all nested constraints. These checks supplement semantic,
policy, security and full runtime E2E tests.

The npm package, Python wheel/sdist and Python executable carry the metaschema
and normalized catalogue beside the contract, so validation does not depend on
a source checkout. Runtime static types ship with their respective packages.
